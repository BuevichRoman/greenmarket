# Артикул продавца как ключ сопоставления при публикации

**Goal:** Публикация перестаёт пересоздавать весь каталог. Строка книги сопоставляется с товаром в базе по артикулу продавца — ключу, который принадлежит продавцу и потому переживает и перепубликацию, и пересоздание книги.

**Дефект:** `kwork/defect_publication_recreates_rows.md`. Сопоставление шло только по `SellerProductId`, который присваивает сервер и который физически нечем доставить в книгу: Service Account читает книгу, но не пишет (CR-001), карточка товара идентификатор не придумывает, эндпоинта со списком товаров нет, а публикация запускается из Личного кабинета — книга ответа публикации не видит. Итог на проде: `created 312, updated 0, deactivated 312` на каждой публикации.

**Почему артикул.** У продавца он уже есть в каждой из 312 строк и уникален. Сейчас лежит внутри текста «Дополнительных характеристик» вместе со страной и датой поставки — а те два значения уже вынесены в свои колонки шаблоном 2.2. Эта правка доделывает тот же перенос для третьего значения.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2.x, MySQL 8.0, pytest. Шаблон книги — Google Sheets, структура задаётся `app/validation/structure_validator.py`.

---

## Решения и их причины

**`SellerProductId` остаётся как есть.** Он по нормативке (`Catalog_Template.md`, «SellerProductId») равен `SellerProduct.id` — суррогатному первичному ключу, на который ссылается `SellerProductPhoto`. Класть в него артикул нельзя: словарь сопоставления построен по целочисленным PK, строка `PROD-1001` до него долетит (модель объявляет поле как `object`, приведения нет) и даст `PublicationConflictError` на всех строках сразу. Внутренний ключ и внешний бизнес-ключ разделяются, а не смешиваются.

**Артикул необязателен на уровне структуры.** У книг шаблонов 2.1/2.2 колонки физически нет, и валидатор терпит недостающие колонки в хвосте. Обязательным артикул становится де-факто для новых книг — через шаблон и инструкцию, а не через отказ публиковать старые.

**Ненайденный артикул — это новый товар, а не конфликт.** Обратное верно для `SellerProductId`: он выдан сервером, и если его нет в базе — книга врёт. Артикул выдаёт продавец, и новая строка с новым артикулом — штатная ситуация.

**Дубль артикула в книге — ошибка публикации.** Иначе две строки схлопнутся в один товар, и продавец молча потеряет позицию.

**Порядок приоритетов при сопоставлении:** артикул → `SellerProductId` → создать. Так книги без артикула продолжают работать ровно как раньше.

## Шаги

- [x] **1. Миграция 018.** `seller_sku VARCHAR(64) NULL` в `SellerProduct` + `UNIQUE (seller_id, seller_sku)`. NULL в MySQL не конфликтуют между собой, поэтому строки без артикула индексу не мешают.
      → verify: миграция применяется на чистой схеме и на схеме с данными.

- [x] **2. Структура шаблона.** `_Column("Артикул продавца", required=False)` в хвост `CATALOG_COLUMNS`; `TEMPLATE_VERSION = "2.3"`, `SUPPORTED_TEMPLATE_VERSIONS` += `"2.3"`; ширина и подсказка колонки в `catalog_template/data.py`.
      → verify: `test_structure_validator`, `test_catalog_template_builder` зелёные; книга 2.2 по-прежнему валидна.

- [x] **3. Модель и маппинг.** `seller_sku` в `PublicationProduct`; `Mapper` читает колонку, пустая ячейка → `None`.
      → verify: тест на книгу с артикулом и на книгу без колонки (шаблон 2.2).

- [x] **4. Валидация уникальности.** `BusinessValidator` проверяет дубли артикула тем же способом, что дубли `SellerProductId`.
      → verify: две строки с одним артикулом дают одну ошибку с номерами строк.

- [x] **5. Хранение.** `seller_sku` в ORM-модели и в `SellerProductRepository.create`.
      → verify: созданный товар сохраняет артикул.

- [x] **6. Сопоставление.** `PublicationService._apply_catalog`: индекс существующих товаров по артикулу; приоритет артикул → `SellerProductId` → создание.
      → verify: повторная публикация той же книги с артикулами даёт `created 0, updated 0, deactivated 0`; переименование товара при том же артикуле — `updated 1`; смена артикула — старый гасится, новый создаётся; книга без артикулов ведёт себя как раньше.

- [x] **7. Нормативка.** Раздел «Артикул продавца» в `Catalog_Template.md` + правило сопоставления в «Изменение»; колонка в `Physical_Model.md`.
      → verify: описанное правило совпадает с реализованным приоритетом.

- [ ] **8. Разовый перенос на проде.** Скрипт: прочитать боевую книгу, сопоставить с существующими строками по названию товара, проставить `seller_sku`. Названия уникальны и в книге, и в базе (312/312) — сопоставление однозначно.
      → verify: 312 строк получили артикул; следующая публикация даёт `created 0, deactivated 0`.

**Вне этой правки:** заполнение колонки в боевой книге. Service Account читает книгу и не пишет — это ручной шаг с аккаунта владельца книги, он предшествует шагу 8.
