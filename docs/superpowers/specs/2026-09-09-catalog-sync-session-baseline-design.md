## 1. Что из ТЗ уже закрыто

Три требования выполнены предыдущими задачами, реализовывать заново нечего:

- **`SellerProduct.version` растёт во всех путях изменения строки**, включая
  публикацию из книги и снятие с витрины (§10, AC-15, Architecture Constraints
  п. 5). Проверено: `publication_service.py:169` и `:177` — обновление строки и
  деактивация пропавшей из книги; `seller_catalog_publisher.py:76` — смена
  видимости при публикации продавца; `seller_catalog_use_case.py:136` — правка.
- **Оптимистическая блокировка** — `expected_version` обязателен, несовпадение
  даёт `409 CATALOG_CHANGED` (PR #43).
- **Идемпотентное создание** — `idempotency_key` уникален в паре с продавцом
  (миграция 020).

**Согласованность снимка (§19) даётся бесплатно.** Прод — MySQL 8.0.36 в
`REPEATABLE READ`: все чтения внутри одной транзакции видят один снимок. Отдельного
механизма не требуется, достаточно строить baseline в одной транзакции.

## 2. Доменная модель

Две сущности. Обе принадлежат домену каталога продавца и живут рядом с
`SellerProduct`, а не в отдельном сервисе (Architecture Constraints, п. 2).

**`CatalogSyncSession`** — рабочая сессия сверки. Владелец — продавец. Имеет
срок жизни и статус. Не хранит содержимого каталога.

**`CatalogSyncBaseline`** — неизменяемый снимок состояния позиции на момент
создания baseline, по строке на позицию. Принадлежит ровно одной сессии.

Baseline не обновляется никогда. Новое исходное состояние — это новая сессия
(§7).

### Состав снимка позиции

ТЗ (§3) перечисляет поля через доменные имена. Соответствие нашей модели:

| ТЗ | Поле `SellerProduct` |
|---|---|
| идентификатор позиции | `id` |
| идентификаторы для matching | `id` + `seller_sku` |
| существование позиции | наличие строки baseline |
| Product association | `product_id` |
| ProductGroup association | выводится из `product_id`, отдельно не хранится |
| name | `seller_name` |
| price | `price` |
| availability | `stock` |
| active/deactivated state | `is_published` |
| остальные поля diff | `unit`, `description`, `origin_country`, `supply_date` |
| version context (§6) | `version` |

Фотографии в baseline не входят (§3, Out of Scope).

**ProductGroup association хранить отдельно не нужно и вредно:** группа
однозначно выводится из позиции справочника, а её дублирование в снимке создало
бы второй источник правды. Если группа сменилась у самой позиции справочника,
это не изменение каталога продавца.

## 3. Модель хранения

```
CatalogSyncSession
    id              BIGINT PK
    session_id      CHAR(36)  UNIQUE      -- то, что видит клиент
    seller_id       INT       NOT NULL
    status          VARCHAR(20) NOT NULL  -- ACTIVE | EXPIRED | COMPLETED | INVALIDATED
    created_at      DATETIME  NOT NULL
    expires_at      DATETIME  NOT NULL
    baseline_created_at DATETIME NULL     -- NULL = baseline ещё нет
    idempotency_key VARCHAR(64) NULL
    UNIQUE (seller_id, idempotency_key)
    INDEX (seller_id, status)

CatalogSyncBaseline
    session_id        BIGINT  FK → CatalogSyncSession.id
    seller_product_id INT     NOT NULL
    PRIMARY KEY (session_id, seller_product_id)
    seller_sku        VARCHAR(64) NULL
    product_id        INT     NULL
    seller_name       VARCHAR(200) NOT NULL
    price             DECIMAL(12,2) NOT NULL
    stock             DECIMAL(12,3) NOT NULL
    unit              VARCHAR(30) NOT NULL
    description       TEXT NULL
    origin_country    VARCHAR(100) NULL
    supply_date       DATE NULL
    is_published      BOOLEAN NOT NULL
    version           INT NOT NULL
```

Решения, которые стоит проговорить:

- **`session_id` — отдельная колонка, а не первичный ключ.** Наружу отдаётся
  UUID: последовательный `id` позволял бы перебирать чужие сессии, а изоляция
  продавцов (AC-09) не должна держаться на одной проверке в коде.
- **`baseline_created_at` вместо отдельного статуса «baseline готов».** Состояние
  «сессия активна, baseline ещё нет» и «активна, baseline есть» — это ровно
  наличие отметки, а не пятый статус. Заодно `NULL` здесь и есть тот замок,
  который не даёт создать второй baseline (см. §5).
- **PK `(session_id, seller_product_id)`** — сурогатный ключ строке снимка не
  нужен, а составной сам запрещает две записи об одной позиции в одном baseline.
- **Ссылки на `SellerProduct` нет.** Baseline обязан пережить удаление позиции —
  «existence» это часть diff. FK сделал бы снимок зависимым от текущего каталога,
  чего он по смыслу быть не должен.

## 4. Жизненный цикл

```
нет сессии
   │ POST /sync-sessions
   ▼
ACTIVE, baseline нет
   │ POST /sync-sessions/{id}/baseline
   ▼
ACTIVE, baseline есть
   ├──► EXPIRED       — по expires_at, вычисляется на чтении
   ├──► INVALIDATED   — см. §6
   └──► COMPLETED     — публикация книги прошла
```

TTL — 24 часа (§2). **Истечение вычисляется при чтении, а не фоновым заданием:**
планировщика в системе нет, а «протухание по расписанию» означало бы, что
статус зависит от того, работал ли воркер. Сессия считается истёкшей, если
`expires_at` в прошлом, независимо от значения `status` в строке.

`COMPLETED` ставит **backend по факту успешной публикации книги**, а не клиент
отдельным запросом. Иначе статус «сверка завершена» можно было бы получить без
завершённой публикации. При неуспешной публикации сессия остаётся `ACTIVE`,
если не истекла и не инвалидирована.

**Очистка ленивая, воркера не заводим.** При обращении к sync-session API
удаляются снимки сессий, которые завершены или истекли: baseline своё отработал,
а его строки — самое объёмное, что тут есть. Сами сессии остаются следом и
удаляются через 90 дней. Состояние «истекла» при этом всегда считается по
`expires_at` и от очистки не зависит.

## 5. Конкурентность

**Второй baseline для сессии физически невозможен.** Создание идёт одной
транзакцией:

```sql
UPDATE CatalogSyncSession
   SET baseline_created_at = :now
 WHERE id = :session_id AND baseline_created_at IS NULL;
```

Ноль затронутых строк означает, что baseline уже создаёт или создал кто-то
другой — запрос отвечает существующим baseline (AC-11) либо `409`, если он ещё
не дописан. Отдельная блокировка не нужна: замком служит сама строка сессии
(AC-12).

**Атомарность (§18, AC-13).** Снимок пишется в той же транзакции, что и отметка
`baseline_created_at`. Частично записанный baseline увидеть нельзя: либо есть
отметка и все строки, либо нет ни того, ни другого. Это же даёт и согласованность
снимка — одна транзакция, `REPEATABLE READ`.

**Повтор запроса (§16, AC-19).** Создание сессии принимает `idempotency_key` по
образцу `POST /seller/products`: ключ уникален в паре с продавцом, повтор
возвращает созданную сессию. Механизм тот же по смыслу, но хранится в своей
таблице — переиспользовать колонку `SellerProduct.idempotency_key` было бы
неверно, это ключ другой сущности.

## 5-bis. Отпечаток книги — шлюз создания baseline

`POST .../baseline` обязательно принимает `sheet_catalog_hash` — отпечаток
состояния книги, посчитанный клиентом. Backend в той же транзакции считает
собственный отпечаток каталога по тем же правилам и сравнивает. Не совпало —
`409`, baseline **не создаётся**. Совпало — снимок фиксируется.

Это настоящий шлюз, а не информационное поле: именно он превращает AC-06 из
утверждения клиента в проверку. При этом книга на сервере не хранится — приходит
только отпечаток, то есть §20 не нарушается.

**Канонизация.** Поля в фиксированном порядке, строки по `seller_product_id`
по возрастанию:

```
seller_product_id, seller_sku, product_id, seller_name,
price, stock, unit, description, origin_country, supply_date, is_published
```

Числа сериализуются строкой в формате колонки (`price` — два знака, `stock` —
три), пустые значения — `null`, кодировка UTF-8, разделители фиксированы.
Правило обязано быть буквально одинаковым на обеих сторонах, иначе шлюз будет
ложно срабатывать.

Не входят: фотографии (§3), `greenmarket_idempotency_key`, `version`,
`moderation_status` и прочие служебные поля.

## 6. Инвалидация

Backend различает три причины (§9):

1. **Истечение** — по `expires_at`, вычисляется на чтении.
2. **Расхождение версий** — при чтении сессии сравнивается `version` из baseline
   с текущим `SellerProduct.version`. Разошлось хотя бы у одной позиции — сессия
   отдаётся с признаком «состояние DB изменилось с момента baseline». Это не
   ошибка и не автоматический перевод в `INVALIDATED`: расхождение DB и SHEET
   после baseline **нормально** и является предметом diff (Additional Context,
   п. 2). Клиент решает, что с этим делать.
3. **Явная инвалидация** — клиент сообщает, что решения больше не применимы.

**Автоматически в `INVALIDATED` backend сессию не переводит**, кроме истечения.
Причина в §9 сформулирована как «backend обнаружил изменение, несовместимое с
текущим reconciliation state», но несовместимость определяется трёхсторонним
сравнением, а SHEET у backend нет (§20). Всё, что backend может увидеть сам, —
расхождение версий, и оно само по себе несовместимости не означает.

## 7. Контракт API

Все эндпоинты — `Authorization: Bearer`, `401` без токена, чужая сессия
неотличима от несуществующей (`404`), как и позиция каталога.

- `POST /api/v1/seller/catalog/sync-sessions` — создать сессию. Тело:
  `{"idempotency_key": str|null}`. Ответ `201`: `session_id`, `status`,
  `created_at`, `expires_at`, `baseline_ready: false`.
- `GET /api/v1/seller/catalog/sync-sessions/{session_id}` — состояние сессии:
  те же поля плюс `baseline_ready` и `db_changed_since_baseline: bool`.
- `POST /api/v1/seller/catalog/sync-sessions/{session_id}/baseline` — создать
  снимок. Тело: `{"sheet_catalog_hash": str}` — обязательно. Ответ `201` — сам
  baseline. Повтор возвращает существующий, `200`. Истёкшая сессия — `409`.
  Расхождение отпечатков — `409` `CATALOG_SHEET_MISMATCH`, baseline не создан.
- `GET /api/v1/seller/catalog/sync-sessions/{session_id}/baseline` — снимок:
  `{"items": [...], "created_at": datetime}`. Состав строки — §2.
- `POST /api/v1/seller/catalog/sync-sessions/{session_id}/invalidate` — явная
  инвалидация.

**Публикация книги становится сессионной, публикация продавца — нет.**
`POST /api/v1/publications` получает `sync_session_id` и требует живую сессию с
готовым baseline. `POST /api/v1/seller/catalog/publish` не меняется: сессия — это
контекст работы с книгой, а не общее разрешение править каталог. Так уже
выкаченный контракт Seller Admin остаётся совместимым.

Отдельного хранилища пользовательских решений не предлагается: ТЗ (§8) разрешает
его не заводить, если состояние безопасно восстанавливается новым diff. Оно
восстанавливается — diff считается из baseline, DB и книги, а решения по нему
принимаются заново. Заводить доменную модель под то, что и так выводится, значит
плодить второй источник правды.

## 8. Решения заказчика и что осталось уточнить

Шесть вопросов закрыты 09.09.2026, решения внесены выше:

1. **Отпечаток книги вводим** — обязательный `sheet_catalog_hash`, реальный
   шлюз, а не информационное поле (раздел 5-bis).
2. **Шлюз сессии — только перед публикацией книги.** `POST /publications`
   получает `sync_session_id`; `POST /seller/catalog/publish` не трогаем.
3. **Очистка:** снимок удаляется у завершённых и истёкших сессий, сессия
   хранится 90 дней. Лениво, при обращении к API, без воркера.
4. **У сессии свой механизм идемпотентности**, ключ `SellerProduct` не
   переиспользуется. Формулировка ТЗ признана ошибочной.
5. **`baseline_ready` — признак, не статус.** Перечисление не расширяется.
6. **`COMPLETED` ставит backend** по факту успешной публикации книги.

### Два уточнения, найденных при сверке набора полей отпечатка

Набор из решения 1 сверен с тем, что реально ходит между книгой и базой
(`mapper.py`, `publication_model.py`, `catalog_template/data.py`). Две правки:

**`origin_country` и `supply_date` в наборе отсутствуют, а должны быть.**
Обе колонки есть в книге («Страна происхождения», «Дата поставки»), обе
редактируются продавцом и обе входят в `EDITABLE_FIELDS`. Если не включить их в
отпечаток, продавец меняет страну происхождения в книге, отпечатки всё равно
совпадают, baseline создаётся при неравных состояниях — и инвариант
`BASELINE = DB = SHEET` нарушается ровно тем шлюзом, который его защищает.
Набор отпечатка обязан совпадать с набором полей diff. В разделе 5-bis они
включены.

**`product_group_id` из набора убран.** Причины две. Он избыточен: группа
однозначно выводится из `product_id`, и если позиции совпали, совпали и группы —
информации отпечатку он не добавляет. И он недоступен клиенту напрямую: книга
несёт название группы («Товарная группа GreenMarket»), а не идентификатор, так
что включение поля заставило бы клиента отображать имя в id перед каждым
подсчётом, с риском разойтись на переименовании группы. То же касается
`product_name`: в книге он есть, в базе выводится из `product_id`.

Если заказчик настаивает на `product_group_id` — вернём, но тогда правило
отображения имени в идентификатор нужно зафиксировать в контракте.

### Совместимость `POST /publications`

Решение 2 меняет уже работающий эндпоинт: книгу публикует Apps Script, и он о
`sync_session_id` ничего не знает. **Нужно решение, обязателен ли новый параметр
сразу.** Если да — публикация из книги перестанет работать до обновления Apps
Script у всех продавцов. Предлагаю принимать его необязательным до появления
Appsmith-сверки и включить обязательность вместе с ней, одним переключением.

## 10. Правки по ревью заказчика (09.09.2026)

Ревью реального диффа. PR #43 одобрен без замечаний, по PR #44 внесено шесть
исправлений.

1. **Канонизация чисел без `float`.** Было `Decimal → float → строка`, что
   вносило двоичное представление в механизм, обязанный давать одинаковый
   результат на двух независимых реализациях. Проверено на конкретном значении:
   `2.675` даёт `2.68` десятичной арифметикой и `2.67` через `float`. Теперь
   `Decimal.quantize`, округление банковское (`ROUND_HALF_EVEN`) и записано в
   контракте — клиенту нужно то же правило.
2. **Один источник состава отпечатка.** `FINGERPRINT_FIELDS` объявлялся, но не
   использовался: payload собирался руками. Список выглядел контрактом, будучи
   декорацией, и добавить поле в одно место, забыв про другое, было делом одной
   правки. Теперь payload строится из него же.
3. **Гонка при создании сессии по ключу.** `SELECT` и `INSERT` шли порознь, и
   одновременный повтор упирался в уникальный индекс, превращаясь в `500`.
   Вставка идёт в `SAVEPOINT`; конфликт означает, что тот же повтор пришёл
   раньше, и возвращается созданная им сессия.
4. **Пустой снимок больше не выдаётся.** Если отметка стоит, а строк нет —
   их дописывает другая транзакция либо снимок уже убран очисткой — ответ
   `409` `BASELINE_IN_PROGRESS`. Прежде клиент мог получить пустой список и
   принять его за пустой каталог.
5. **Переходы `invalidate`.** Правило зафиксировано: `ACTIVE` инвалидируется;
   уже инвалидированная и истёкшая отвечают успехом, потому что намерение по
   ним и так выполнено; `COMPLETED` — `409`, объявить состоявшуюся публикацию
   брошенной нельзя.
6. **`baseline_ready` считается по строкам, а не по отметке.** Ленивая очистка
   в том же запросе могла удалить снимок завершённой сессии, и ответ «снимок
   есть» противоречил бы пустой выдаче `/baseline`.

Добавлены тесты: гонка создания сессии по ключу, параллельное создание снимка,
запрет инвалидации завершённой сессии, безвредность инвалидации истёкшей,
появление позиции после снимка и снятие с витрины как изменения DB. Последние
два — по требованию ревью закрепить инвариант «любое изменение
sync-полей меняет `version`» именно на добавлении и снятии.

Замечание ревью о том, что сериализация на стороне книги ещё не написана,
принято к сведению: PR закрывает backend-зависимость, но не сам workflow
сверки. Требование обязательного `sync_session_id` в `POST /publications`
ревью снял — точка вызова появится вместе с реализацией сверки.

708 тестов.
