## 1. Результат исследования

Проверены `docs/04-services/REST_API.md`, `docs/04-services/API_Backlog.md`, `docs/02-domain/Domain_Model.md`, `docs/03-database/Physical_Model.md`, `docs/03-database/Database_Migrations.md` и `docs/01-overview/Scope.md`.

Подтверждено:

- Seller Catalog API предоставляет `GET /api/v1/seller/products`, `GET /api/v1/seller/products/{id}`, `POST /api/v1/seller/products` и `PATCH /api/v1/seller/products/{id}`.
- `SellerProduct.stock` — текущий остаток; PATCH требует `expected_version` и отклоняет устаревшую версию с `409 CATALOG_CHANGED`.
- Для создания позиции уже существует `idempotency_key`, но это защита создания SellerProduct, а не регистрации продажи или поступления.
- В нормативной модели Stage 1 нет сущностей продажи, поступления, складской операции или журнала изменения остатка. Нет документированных API регистрации таких операций.
- Нормативный `Scope.md` прямо исключает коммерческие процессы Stage 1. Добавление продаж/поступлений требует решения о новом этапе/объёме и ADR.

**Вывод:** существующий PATCH остатка не подходит в качестве API продажи/поступления. Он не сохраняет тип операции, количество до/после, причину изменения и ключ идемпотентности операции. Использовать его как замену регистрации продажи небезопасно.

## 2. Границы реализации

До появления backend-контракта не вносить в Seller Catalog Widget код, который изменяет остаток при распознавании фраз «продал» или «принял». Нельзя подменять бизнес-операцию прямым изменением `stock`, локальным журналом или записью в БД из UI.

Текущий этап — подготовка контракта. В репозитории `BuevichRoman/greenmarket` доступны нормативная документация и Seller Catalog Widget; отдельный backend-контракт операций продаж/поступлений в проверенных документах отсутствует. Репозиторий `j7018515/universal-backend-src` описывает другой Universal API в `public_html/taxi/` и не подтверждает наличие GreenMarket Seller Catalog backend; его нельзя считать реализацией этого API без отдельной проверки интеграции.

## 3. Предлагаемый контракт для согласования

Это **предложение**, а не описание уже существующего API.

### Команда

Один ресурс регистрации складской операции продавца, например `POST /api/v1/seller/stock-operations`.

Запрос после подтверждения продавцом:

```json
{
  "idempotency_key": "uuid",
  "operation": "SALE",
  "seller_product_id": 123,
  "quantity": "5",
  "unit": "кг"
}
```

Для поступления `operation = "INCOMING"`. Продавец определяется только по Bearer-токену, а не по переданному клиентом `seller_id`. Поля количества и единицы должны пройти серверную валидацию относительно единицы SellerProduct; автоматическая конвертация единиц не допускается без утверждённого правила.

### Семантика

- `SALE`: уменьшить остаток на указанное количество; отрицательный остаток запрещён, если продукт отдельно не утвердит иной режим.
- `INCOMING`: увеличить остаток на указанное количество.
- Операция и изменение остатка выполняются атомарно в одной транзакции.
- Сервер проверяет принадлежность позиции продавцу, активность продавца и актуальное состояние позиции.
- Один `idempotency_key` в рамках продавца с тем же payload возвращает результат первоначальной операции без повторного изменения остатка.
- Повтор ключа с другим payload отклоняется `409 IDEMPOTENCY_KEY_REUSED`.
- Конкурирующие запросы с одним ключом не могут создать две операции или дважды изменить остаток.
- Для продажи недостаточного остатка — отказ без изменения данных.
- Успех показывается в UI только после подтверждённого ответа сервера. Таймаут означает неизвестный результат: повторяется запрос с тем же ключом, не создаётся новый.
- Ответ должен содержать идентификатор операции, тип, товар, количество, единицу, остаток до/после и время выполнения. Точные коды ошибок и схема ответа должны быть оформлены в OpenAPI и нормативном REST API до реализации UI.

### Хранение

Предлагается отдельный неизменяемый журнал операций, содержащий как минимум: идентификатор, продавца, SellerProduct, тип операции, количество, единицу, остаток до/после, idempotency key, автора/время и идентификатор запроса. Точный DDL, индексы, уникальные ограничения и стратегия блокировки строки определяются после изучения фактического backend и принятия ADR. Нельзя утверждать, что эта таблица уже существует.

## 4. Требования к голосовому UI

1. Распознавание не выполняет запись.
2. Парсер извлекает тип операции, товар, количество и единицу.
3. Если товар не найден или найдено несколько вариантов — запись невозможна до явного выбора.
4. Несовпадение единицы товара и команды блокирует операцию; конвертация возможна только по утверждённому серверному правилу.
5. Перед записью отображается подтверждение: «Продажа/Поступление — товар — количество — единица».
6. Отмена не вызывает API.
7. После подтверждения UI создаёт один idempotency key и сохраняет его для всех повторов этой команды.
8. Повторное нажатие блокируется интерфейсом, но защита от дублей обязательна на сервере.
9. При ошибке или таймауте UI не объявляет операцию выполненной.
10. Доступ к данным — только через утверждённый host/API-контракт, без прямого доступа UI к БД.

## 5. Обязательные тесты

- продажа уменьшает остаток ровно один раз;
- поступление увеличивает остаток ровно один раз;
- отмена подтверждения не меняет данные;
- точное название разрешается в ожидаемый SellerProduct;
- неоднозначное название требует выбора;
- единица команды не совпадает с единицей товара — отказ;
- нулевое, отрицательное и некорректное количество — отказ;
- продажа больше остатка — отказ без частичного изменения;
- товар другого продавца — отказ;
- повтор ключа с тем же payload возвращает первоначальный результат;
- повтор ключа с другим payload — конфликт;
- два параллельных запроса с одним ключом меняют остаток один раз;
- повтор после таймаута с тем же ключом не дублирует операцию;
- ошибка сервера не отображается как успех;
- остаток после операции совпадает с серверным ответом и повторным GET.

Голосовой UI использует событие Appsmith onStockOperation. Чтобы операция реально проходила end-to-end, host должен отправлять pending на POST /api/v1/seller/stock-operations с Bearer-токеном и затем записывать в модель stockOperationResult объект { idempotency_key, ok, known, response, error, at }. ok=true допустим только после успешного ответа API; сетевой таймаут должен выставлять known=false и оставлять результат неизвестным и позволять повторить тот же payload с тем же ключом. Это соединение Appsmith с API требует проверки в целевом приложении, поскольку конфигурация запросов Appsmith не хранится в этом репозитории.

PR остаётся Draft. CI ещё должен завершиться успешно; тесты реальной MySQL-транзакции/конкурентности и применение миграции на тестовой БД не подтверждены. Не вливать и не деплоить до успешных проверок и согласованного расширения Scope.
