# Seller Catalog API — восстановленный контракт

**Статус:** черновик, на сверку. Нормативным не является.
Дата: 07.09.2026

Текст согласованного ТЗ на доработку backend в репозиторий не попал. Контракт
ниже восстановлен из трёх источников, которые в репозитории есть:

- `docs/04-services/REST_API.md` — соглашения проекта (префикс, конверт ошибок,
  пагинация, схема аутентификации Admin API, состав `GET /catalog/sellers/{id}/products`);
- `appsmith/seller-catalog-widget.html` — блок «КОНТРАКТ С ХОСТОМ», функция
  `fromApi` (строки 810–840) и события виджета: это прямая заявка потребителя
  на состав полей;
- `backend/app/infrastructure/models.py:84` — `SellerProduct`, `SellerProductPhoto`:
  чем система реально располагает.

Расхождения между источниками не сглажены, а вынесены в раздел «Расхождения» —
их закрывает решение, а не догадка.

---

## 1. Аутентификация

Все эндпоинты раздела требуют `Authorization: Bearer <access_token>`, где
`access_token` — существующий бессрочный токен продавца из таблицы `Seller`
(выдаётся `POST /api/v1/seller/activate`, резолвится
`resolve_seller_access`, `backend/app/publication/seller_access.py:14`).
Новой аутентификации не вводится — это прямо запрещено разделом Out of Scope
ТЗ «Единый Seller Admin».

Токен в query-строке не принимается. Основание — то же, что уже записано для
Admin API (`REST_API.md`, раздел «Admin API»): query целиком пишется в
`access.log` nginx. Существующий Seller API токен в query принимает; миграция
legacy-эндпоинтов на заголовок — отдельная задача, здесь требование
распространяется только на новый контур.

`seller_id` из запроса не принимается ни в каком виде — он выводится из токена.
Это то же правило, которым 19.07 закрыли дыру в `POST /publications`.

## 2. Ресурсы

Префикс раздела — `/api/v1/seller/catalog/products`. Имя `/seller/catalog` уже
занято статус-сводкой (`is_active`, `current_catalog_version`, …), поэтому
позиции живут на вложенном ресурсе, а не заменяют собой существующий ответ.
См. расхождение 9.

### 2.1. `GET /api/v1/seller/catalog/products`

Построчный каталог продавца — то, чего сегодня нет ни в одном эндпоинте.

Параметры: `group_id`, `search`, `page`, `limit`, `sort` (`name`|`price`|`updated_at`),
`is_published` (`true`|`false`), `moderation_status` (`RESOLVED`|`WAIT_PRODUCT`).
Первые пять — как в `GET /catalog/products`, включая перечисление нескольких
категорий и разворот группы на всю ветку. Последние два нужны фильтрам виджета
и в публичном каталоге смысла не имеют.

Ответ: `{"products": [...], "page": int, "limit": int, "total": int}`.

Состав строки и соответствие источникам:

| Поле виджета | Поле ответа | Источник | Есть в публичном каталоге |
|---|---|---|---|
| `id` | `seller_product_id` | `SellerProduct.id` | да |
| `global_product_id` | `product_id` | `SellerProduct.product_id` | да |
| `product_name` | `name` | `SellerProduct.seller_name` | да |
| — | `catalog_name` | `Product.name` | да, виджет не использует |
| `group` | `group_name` | `Product` → `ProductGroup.name` | да |
| `price` | `price` | `SellerProduct.price` | да |
| `stock` | `stock` | `SellerProduct.stock` | да |
| `unit` | `unit` | `SellerProduct.unit` | да |
| `description` | `description` | `SellerProduct.description` | да |
| `origin_country` | `origin_country` | `SellerProduct.origin_country` | да |
| `delivery_date` | `supply_date` | `SellerProduct.supply_date` | да |
| `photos`, `photo_url`, `has_photo` | `photos: [str]` | `SellerProductPhoto` по `sort_order` | да |
| `publication_status` | `is_published: bool` | `SellerProduct.is_published` | **нет** |
| `moderation_status` | `moderation_status` | `SellerProduct.moderation_status` | **нет** |
| `seller_sku` | `seller_sku` | `SellerProduct.seller_sku` | **нет** |
| `updated_at` | `updated_at` | `SellerProduct.updated_at` | **нет** |
| `seller_name` (имя продавца) | — | — | **нет**, см. расхождение 4 |

Три отличия от `GET /catalog/sellers/{id}/products`, ради которых раздел и нужен:

1. **Видимость.** Публичный каталог отдаёт только видимые предложения —
   промодерированные и опубликованные. Здесь продавец обязан видеть свой
   каталог целиком, включая `product_id IS NULL` и `is_published = FALSE`:
   иначе позиция, ожидающая модерации, для него просто исчезает.
2. **`is_published` и `seller_sku`** в публичном ответе отсутствуют — первое
   покупателю не нужно, второе является внутренним ключом продавца.
   Это ровно те два поля, которые виджет отмечает как недостающие
   (`appsmith/seller-catalog-widget.html:812`).
3. **Деактивированный продавец** получает свой каталог, а не `404`. Публичный
   эндпоинт отдаёт `404 NOT_FOUND`, чтобы перебором нельзя было выяснить, кто
   деактивирован; здесь запрашивающий — сам продавец, скрывать не от кого.
   То же решение уже принято для профиля (`GET /seller/profile`, 05.08).

`publication_status` виджета сервер не возвращает. `PUBLISHED`/`UNPUBLISHED` —
это `is_published`, а `DIRTY` в системе не существует вовсе, см. расхождение 1.

### 2.2. `POST /api/v1/seller/catalog/products`

Создать позицию (`onAddProduct`). Тело — `name`, `price`, `stock`, `unit`,
обязательны; `description`, `origin_country`, `supply_date`, `seller_sku` —
необязательны. `product_id` в теле не принимается: связь со справочником
ставит только модератор (`PUT /api/v1/admin/moderation/{id}`), поэтому новая
позиция всегда рождается с `product_id = NULL`, `moderation_status = WAIT_PRODUCT`
и `is_published = FALSE`.

Ответ `201` — объект позиции того же вида, что в списке.
`409 SELLER_SKU_ALREADY_EXISTS` — артикул занят другой позицией этого продавца
(ограничение `uk_SellerProduct_seller_sku (seller_id, seller_sku)`, миграция 018;
в `models.py` оно не отражено, но в БД есть). `422 VALIDATION_ERROR` — остальное.

### 2.3. `PATCH /api/v1/seller/catalog/products/{id}`

Одним эндпоинтом закрываются оба события правки: `onPatchField` (инлайн-правка
цены и остатка) шлёт один ключ, `onSaveProduct` (сохранение карточки) — несколько.
Разделять их на два ресурса незачем: разница только в числе ключей.

Семантика тела повторяет уже согласованный `PUT /api/v1/seller/profile`:
правятся только переданные ключи, отсутствие ключа означает «не трогать»,
лишние ключи запрещены (`extra="forbid"` — молчаливое игнорирование опечатки
в имени поля неотличимо от успешного сохранения). Ответ — `{"changed": [str]}`,
имена реально изменившихся полей; повторная отправка тех же значений возвращает
пустой список, и это успех, а не отказ.

Правятся: `name`, `price`, `stock`, `unit`, `description`, `origin_country`,
`supply_date`, `seller_sku`.

Не правятся и в теле запрещены: `product_id` (модерация), `moderation_status`
(выводится из связи, инвариант закреплён миграцией 014), `photos`
(отдельный ресурс, см. 2.4), `is_published` (см. расхождение 2).

`404 SELLER_PRODUCT_NOT_FOUND` — позиции нет **либо** она принадлежит другому
продавцу. Два случая намеренно неразличимы: иначе перебором `id` выясняется
состав чужого каталога. Это и есть техническая реализация AC-6 ТЗ.

### 2.4. `PUT /api/v1/seller/catalog/products/{id}/photos`

Тело `{"photo_ids": [int]}` — задаёт и состав, и порядок показа: `sort_order`
равен индексу в массиве. Пустой массив снимает все фотографии.
Ответ — `{"photos": [str]}`, готовые URL в новом порядке.

Этот эндпоинт закрывает разрыв, который сегодня существует: `POST /api/v1/photos`
загружает файл и создаёт `Photo`, но **связь с товаром не создаёт** — она
появляется только при следующей публикации из книги, через колонку «Фото»
(`REST_API.md`, Publication API). Вне книги фотографию привязать нечем, то есть
пункты ТЗ про управление фотографиями сегодня нереализуемы в принципе.

Порядок работы виджета: файлы приходят в `onSaveProduct` внутри `photos` как
data URL, хост загружает каждый через `POST /api/v1/photos` и получает
`photo_id`, затем шлёт весь список сюда. Загрузку файла оставляем на
существующем эндпоинте — новый ресурс отвечает только за связь.

`404 PHOTO_NOT_FOUND` — фотография не существует или загружена другим продавцом.

## 3. Ошибки

Конверт — общий для API: `{"error": {"code", "message", "details"}}`.
Коды: `SELLER_ACCESS_DENIED`, `SELLER_PRODUCT_NOT_FOUND`, `PHOTO_NOT_FOUND`,
`SELLER_SKU_ALREADY_EXISTS`, `VALIDATION_ERROR`.

## 4. Расхождения — нужно решение

Это места, где источники противоречат друг другу или системе. Каждое меняет
контракт, поэтому угадывать их нельзя.

1. **`DIRTY` не существует на сервере.** Виджет ставит этот статус локально при
   правке (строка 877) и снимает после `onPublish`. В БД есть только
   `is_published: bool`. После перезагрузки страницы все правки будут выглядеть
   опубликованными. Нужен ли серверный признак «изменено после публикации»
   (лишняя колонка + правило её сброса) или `DIRTY` остаётся чисто экранным
   состоянием сессии — и тогда это надо честно записать в ТЗ.

2. **Поштучная публикация против дифа из книги.** Виджет шлёт
   `onPublish({ids})` — «опубликовать вот эти позиции». Существующий
   `POST /api/v1/publications` устроен иначе: он приводит весь каталог продавца
   к содержимому Google-таблицы и снимает с публикации всё, чего в ней нет
   (`publication_service.py:204-209`). Поштучного эндпоинта публикации нет,
   и добавить его к текущей модели нельзя, не решив сначала вопрос из §4 ревью:
   один каталог — один режим ведения. **Это самая дорогая развилка контракта,
   и до её закрытия эндпоинт публикации в этом разделе не описывается.**

3. **Группа у непромодерированной позиции.** Виджет показывает `group` у всех
   строк и даёт выбрать её в карточке нового товара (строка 1460, `blank.group`).
   Источника нет: группа приходит из `Product` → `ProductGroup`, а у новой
   позиции `product_id IS NULL`. Варианты: отдавать `group_name: null` и
   рисовать «на модерации» (дёшево, но карточка теряет поле), либо завести у
   `SellerProduct` поле «предложенная группа» как подсказку модератору
   (миграция + смысл, который надо описать в домене).

4. **Коллизия имени `seller_name`.** В виджете `seller_name` — название
   хозяйства; в БД `SellerProduct.seller_name` — наименование товара, данное
   продавцом. Публичный API уже разводит их как `name` (своё) и `catalog_name`
   (эталонное), а имя продавца там вообще не в этом ответе, оно в
   `GET /catalog/sellers/{id}`. В контракте выше я оставил `name`/`catalog_name`
   и имя продавца из ответа убрал: раздел и так работает в контексте одного
   продавца, повторять его имя в каждой строке незачем — виджет возьмёт его
   из статус-сводки. Нужно подтвердить.

5. **`catalog_name` виджет не показывает.** Эталонное наименование в ответе есть,
   но на экране его нет — продавец не увидит, с какой позицией справочника
   сопоставлен его товар. Для модерации это ровно та информация, которой он
   ждёт. Добавлять в UI или сознательно не показывать?

6. **Нет удаления и снятия с публикации.** Событий у виджета пять, ни одно из
   них не удаляет позицию и не снимает её с витрины. В книге это делается
   удалением строки. Если Seller Admin становится вторым режимом ведения
   каталога (см. расхождение 2), операция обязана появиться — иначе позицию,
   заведённую здесь, нечем убрать. Проектное решение — `is_active`-подобное
   снятие, а не `DELETE`: так уже сделано для `Product` и групп.

7. **`401` или `403` на плохой токен.** Сегодня Seller API отвечает `403
   SELLER_ACCESS_DENIED`, Admin API — `401 ADMIN_ACCESS_DENIED`, и разница
   в `REST_API.md` обоснована: у продавца токен идентифицирует уже известного
   продавца, у админа запрос просто неаутентифицирован. Новый контур — Bearer,
   то есть ровно «просто неаутентифицирован». Оставить `403` ради единообразия
   с Seller API или взять `401` ради единообразия со схемой Bearer?
   В контракте выше оставлен `403` — как в разделе, к которому эндпоинты
   принадлежат.

8. **`POST /api/v1/photos` остаётся на `access_token` в теле** (multipart), то
   есть не Bearer. Формально это нарушает требование «единая аутентификация
   раздела», фактически — трогать работающую загрузку из книги ради
   единообразия рискованно. Предлагаю принимать оба способа: заголовок, если
   он есть, иначе поле тела. Нужно подтвердить.

9. **Именование.** `/seller/catalog/products` выбрано потому, что
   `/seller/catalog` занято статус-сводкой. Альтернатива — переименовать
   существующий эндпоинт в `/seller/catalog/status` и освободить
   `/seller/catalog` под список (честнее по смыслу: «catalog» логичнее означает
   каталог, а не сводку), но это ломает Apps Script и Seller Cabinet.
   Оставляем как есть или ломаем сейчас, пока потребителей мало?

10. **Публичный `GET /catalog/sellers/{id}/products` не отдаёт `seller_name`
    продавца**, хотя `fromApi` его читает (`row.seller_name || ''`). Сегодня
    виджет на боевых данных всегда получит пустую строку. Это дефект самого
    виджета, а не контракта, но чинить надо там же.

## 5. Чего этот документ не описывает

- Эндпоинт публикации — заблокирован расхождением 2.
- Аутентификацию продавца как человека (логин, сессия, logout) — предмет
  вопроса A/B из §2 ревью, решает заказчик.
- Миграцию legacy Seller API на заголовок — отдельная задача.
